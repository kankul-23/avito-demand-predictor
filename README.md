# Avito Demand Predictor

Предсказание вероятности успешной продажи объявления на Avito по данным,
доступным **в момент публикации** — без post-event признаков (просмотров,
кликов, факта продажи), чтобы модель была применима в реальном времени,
а не только на исторических данных.

## Задача

Бинарная классификация вместо регрессии по исходной `deal_probability`:
распределение целевой переменной сильно zero-inflated (~65% объявлений
с вероятностью 0, ~0.67% — с гарантированной 1) — регрессия на такой форме
работает плохо, метрики устойчивые к дисбалансу подходят естественнее.

**Метрики:** ROC-AUC и PR-AUC — не требуют выбора порога, оценивают
качество ранжирования само по себе.

**Валидация:** time-based split (train строго до, test строго после
по `activation_date`) — обычный random K-Fold дал бы завышенную оценку
за счёт "подглядывания" в будущее.

## Результаты

| Модель | ROC-AUC | PR-AUC |
|---|---|---|
| **CatBoost** (финальная) | **0.838** | **0.516** |
| LightGBM | 0.836 | 0.507 |
| LogisticRegression (baseline) | 0.812 | 0.449 |

Три модели сравнены на идентичном признаковом пространстве (25 признаков)
и одном time-based split — различается только финальное кодирование
признаков под конкретную библиотеку. Полная таблица и топ-10 важности
признаков по каждой модели — [`models/model_comparison.json`](models/model_comparison.json).

Гиперпараметры CatBoost подобраны через Optuna (TPE, 15 испытаний);
поиск прогнан дважды на разных диапазонах, чтобы убедиться, что
результат не упирается в границу пространства поиска — оба прогона
сошлись с точностью до 4-го знака.

**Продуктовый порог бинаризации предсказаний:** `0.30`, подобран по сетке
F1/F0.5/F2 на валидации — почти на пике F1, но с заметно лучшим precision
(обоснование: ложная рекомендация платного продвижения напрямую бьёт
по доверию продавца к платформе).

## Error Analysis

Построчный анализ ошибок (`TP`/`TN`/`FP`/`FN`) по категориям и ценовым
сегментам выявил систематическое завышение оценки в категории
"Автомобили" и "Предложение услуг". Знаковый SHAP-анализ (сравнение FP
vs TN внутри категории) подтвердил конкретный механизм: признак
`price_to_cat_median` меняет знак влияния между TN (тянет предсказание
вниз, корректно) и FP (тянет вверх) — воспроизводимый сбой логики
признака, а не просто корреляция.

## Архитектура

```
Сырые данные (CSV)
        │
        ▼
┌────────────────────┐
│ Feature Engineering │  25 признаков: цена/медианы, частоты,
│  (fit/transform)    │  seller activity, text length, TF-IDF/native text
└────────────────────┘
        │
        ▼
┌────────────────────┐
│   CatBoost model     │  ROC-AUC 0.838 / PR-AUC 0.516
└────────────────────┘
        │
        ▼
┌────────────────────┐
│  FastAPI /predict     │  вероятность + бинарная рекомендация
│   (Docker-образ)      │  по продуктовому порогу 0.30
└────────────────────┘
```

Все три модели обучаются на общем `FeatureEngineeringPipeline`
(`src/features/build_features.py`) — гарантирует честное сравнение:
разница в метриках отражает архитектуру моделей, а не разное
признаковое пространство.

## Стек и структура

- **Данные и признаки:** pandas, numpy, scipy, pyarrow
- **Модели:** CatBoost, LightGBM, scikit-learn, Optuna
- **Трекинг экспериментов:** MLflow (Tracking; параметры, метрики,
  top-10 feature importance по каждому run)
- **API:** FastAPI + Pydantic — `/predict` (вероятность + рекомендация
  продвижения), `/health`
- **Тесты:** pytest, 24 теста на API (валидация, применение порога,
  обработка ошибок), модель замокирована — тесты проверяют логику
  сервиса, не качество предсказаний
- **Контейнеризация:** Docker — образ с запечённой моделью, самодостаточен

```
src/
├── api/           # FastAPI-сервис (main.py, schemas.py)
├── data/          # загрузка и препроцессинг
├── features/       # FeatureEngineeringPipeline + модель-специфичное кодирование
├── models/         # обучение трёх моделей, инференс, error analysis, SHAP
└── utils/          # метрики, подбор порога бинаризации
scripts/            # сравнение моделей, тюнинг, MLflow-логирование
tests/              # pytest-сьют для API
```

## Быстрый старт

```bash
# Через Docker (модель уже запечена в образ)
docker build -t avito-demand-predictor .
docker run -p 8000:8000 avito-demand-predictor

# Прогон тестов API (24 теста, модель замокирована)
pip install -r requirements.txt
pytest tests/ -v
```

Документация API (Swagger UI) после запуска — `http://localhost:8000/docs`.

## Осознанные ограничения

- **`image_top_1`** — числовой ID категории изображения, заранее
  посчитанный сторонней моделью компьютерного зрения при сборке исходного
  датасета. Модель использует это число как обычный признак, не "видит"
  само изображение. Для нового объявления через API этот ID взять
  неоткуда без отдельной модели CV — сознательно вне скоупа проекта,
  поле в API опционально.
- **MLflow Model Registry** не подключён — для пет-проекта без реального
  сценария автоматического деплоя это сложность ради сложности; модель
  в API грузится напрямую с диска.
- **`/predict` принимает одно объявление за запрос**, не массив —
  соответствует реальному сценарию (продавец публикует объявления по
  одному); расширение до batch несложное, `predict()` уже принимает
  `DataFrame` любой длины.
